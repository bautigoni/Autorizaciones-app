# CLAUDE.md

Guidance for Claude Code (or any contributor) working on this repository.

## Project overview

**Salida Segura** is a full-stack web app that centralizes the workflow of authorizing early/non-standard student pick-ups in a school. It coordinates families, school staff (preceptor / secretariat / dirección), and gate security around a single, audited authorization record.

Tech: **Vite + React + TypeScript** on the client, **Express + better-sqlite3** on the server, **Tailwind CSS** for styling, **React Router** for navigation. Everything ships as one Node project.

## Commands

```bash
npm install              # install everything
npm run db:seed          # create + seed data/salida-segura.db
npm run dev              # parallel: tsx watch server + vite dev
npm run dev:client       # vite only (port 5173)
npm run dev:server       # api only (port 5174)
npm run db:reset         # wipe DB and reseed
npm run build            # build client to dist/
```

Vite proxies `/api/*` to the Express server, so the frontend talks to a single origin.

## Architecture

```
client (React/Vite)  ── /api ──▶  Express  ──▶  better-sqlite3 ──▶  data/salida-segura.db
```

- **No client-side mock data.** Components fetch from `/api/*` through `src/services/api.ts`. The DB is the source of truth.
- **Session** is intentionally minimal: a successful `/api/auth/login` returns the user; the client stores it in `localStorage` and forwards the user id back via the `x-user-id` header. (Demo only — swap for real auth/JWT before production.)
- **Types** are shared between client and server via `shared/types.ts`. Use these types end-to-end; don't redeclare them per layer.
- **Domain logic lives in `server/services/`.** Routes in `server/index.ts` should stay thin and delegate. When adding a new entity, create a service file in the same pattern.
- **Audit history is automatic.** Any status change goes through `updateStatus` / `registerWithdrawal` / `cancelAuthorization`, which write a row to `auth_history`. Don't update statuses by raw UPDATE — use the service.
- **Codes (`SS-0001`) are generated by `nextAuthCode()`** in `server/db/index.ts`. Don't generate them client-side.

## Frontend conventions

- **Routing:** `src/App.tsx` defines `/familia`, `/cole`, `/porteria` trees, each wrapped by a layout and gated by `RequireRole`. Root `/` redirects to the user's role home.
- **Layouts:** `FamilyLayout` (mobile-first with bottom nav + FAB), `InternalLayout` (sidebar on lg+, top tabs on mobile), `GateLayout` (centered, high-contrast top bar).
- **Components in `src/components/`** are the design system. Always prefer them to raw HTML controls:
  - `Button`, `Input`, `Textarea`, `Select`, `Checkbox` / `Radio` / `Switch`, `Modal`, `Drawer`, `StatusBadge`, `Pill`, `Avatar`, `Logo`, `EmptyState`, `LoadingState`, `ErrorState`, `Toast`.
  - **Never render native `<select>` / `<input type=checkbox>` / `<input type=radio>` in pages** — they look broken with the warm theme. Use the custom components instead.
- **Tailwind:** custom palette in `tailwind.config.js` — `cream`, `peach`, `coral`, `sage`, `ink`, `warm.line`, `warm.surface`. Use semantic gradients like `bg-gradient-soft`, `bg-gradient-warm`, `card-gradient`. Avoid hardcoded hex.
- **Status badges:** always use `<StatusBadge status={a.status} />` — colors and labels are centralized in `Badge.tsx`.

## Styling rules

- Always design **empty, loading, and error states** — every list has `<EmptyState />` / `<LoadingState />` paths.
- Cards use the `card` or `card-gradient` utility (defined in `index.css`). Don't introduce ad-hoc white boxes.
- Modals/drawers come from `components/Modal.tsx`. They include scroll-locking, ESC-to-close, gradient header.
- Toasts come from `useToast()` (`components/Toast.tsx`). Always toast user-visible mutations.
- For interactive surfaces, use `hover:shadow-glow`, `focus-within:shadow-ring`, and the `transition` utility for movement.

## Backend conventions

- **Validation:** the API trusts the client minimally — required fields are checked, but full Zod-based validation is a TODO. When tightening, put schemas next to the route in `server/index.ts` or move routes into `server/routes/`.
- **Status transitions:** valid status set is in `shared/types.ts > AuthStatus`. The SQLite CHECK constraint mirrors it. If you add a status, update **both**.
- **Migrations:** the project applies `schema.sql` on every startup via `db.exec(schema)` (CREATE TABLE IF NOT EXISTS). For schema changes, either:
  1. Add additive DDL to `schema.sql` (safe for IF NOT EXISTS / new columns) **and** a migration block, or
  2. Run `npm run db:reset` during local dev.
- **Auto-expiry:** `expireOld()` runs once on server start and moves stale `pending/approved/observed` rows older than today to `expired`, with a history row. If you need it scheduled, add a `setInterval`.

## Adding a feature — typical flow

1. Add or extend a type in `shared/types.ts`.
2. Add columns / tables to `server/db/schema.sql` and (if non-trivial) seed data in `server/db/seed.ts`.
3. Add domain logic to `server/services/<entity>.ts`.
4. Expose a thin HTTP route in `server/index.ts`.
5. Add a client method to `src/services/api.ts`.
6. Build the page in `src/pages/<role>/...` using the design-system components in `src/components/`.
7. Wire the route in `src/App.tsx`, behind the right `RequireRole`.

## Things to NOT do

- Don't hardcode app data in components. Always read from the API.
- Don't render native form controls in user-facing pages.
- Don't bypass the service layer when changing authorization state.
- Don't generate authorization codes on the client.
- Don't introduce new color tokens outside the Tailwind config.
- Don't `--amend` an existing commit or skip hooks.
